# Альтернативное размещение SQLite на постоянном диске

Этот профиль предназначен для VM с постоянным диском и одним Docker-контейнером API.
Выбранная схема Render Free + Supabase описана в [deployment.md](deployment.md).

## Совместимый перенос текущей версии на VM

Нужны Linux, Docker Compose, постоянный диск, исходящий HTTPS, один API-процесс и
HTTPS-домен. SQLite подходит для текущего небольшого односерверного приложения.
Нельзя запускать несколько реплик с отдельными копиями рабочей БД.

Постоянный `/app/data` содержит:

- `local.db` — база приложения;
- `media/` — загруженные фотографии;
- `sports-sync/` — проверенные манифесты, расписание, FIBA watchlist и портреты;
- `backups/` — дневные резервные копии.

Независимую резервную копию этого набора храните вне VM. Снимок БД делайте через
SQLite backup API, а не обычным копированием открытого `.db`. При переносе исключите
одновременное редактирование и загрузку фотографий. Локальные активные сессии не нужно
переносить на публичный сервер; после переноса войдите заново.

Экспортируйте рабочую базу и фото из корня backend (реальные пути при необходимости
задайте через `--database` и `--media`). Каждому экспорту нужен новый каталог:

```powershell
.venv/Scripts/python.exe scripts/export_deployment.py export --output data/deployment/my-transfer
.venv/Scripts/python.exe scripts/export_deployment.py verify --bundle data/deployment/my-transfer
```

Скрипт использует SQLite backup API, удаляет сессии только из копии, добавляет фото и
рабочие файлы синхронизации. `manifest.json` содержит размеры и SHA-256 всех файлов.
Каталог приватный: в нём остаются аккаунты и хеши паролей. Файлы `.env`, ключи и
журналы не включаются. В примере ниже `./bundle` означает этот проверенный каталог,
перенесённый на сервер. Перед копированием повторите `verify` на сервере.

1. Перенесите исходники и проверенный набор данных по SSH. Файлы `.env`, ключи,
   приватные архивы, рабочую БД и `local-admin-credentials.json` не публикуйте в GitHub.
2. На сервере скопируйте `.env.production.example` в `.env.production` и заполните
   `APP_PUBLIC_ORIGIN` точным HTTPS origin фронта, без `/repository/` и завершающего `/`.
   Для Caddy добавьте `API_DOMAIN=api.club.example` без `https://`.
3. Только при первом переносе создайте **новый пустой** постоянный volume и перенесите данные в `/app/data` до первого запуска
   API. `docker compose ... create migrate` создаёт volume без запуска миграций;
   используйте `docker compose ... cp` для переноса каталога данных в контейнер
   `migrate`. Пример ниже. Пользователь `app` должен иметь право записи.
4. Настройте DNS `API_DOMAIN` на IP сервера и откройте TCP 80/443 (UDP 443 опционален).
   Caddy выдаст и продлит сертификат при доступном DNS и открытых портах.
   API доверяет forwarded headers только выделенной сети API↔Caddy. Не подключайте
   к ней другие контейнеры. При конфликте адресов задайте свободный private IPv4
   CIDR в `PB_PROXY_SUBNET`: он одновременно задаёт IPAM сети и список доверия API.
5. Запустите миграции и API, затем проверьте `/health/ready` и данные сезона 2026/27.
   Создание нового администратора выполняется штатной CLI на сервере; перенесённые
   аккаунты сохраняются. Команды сброса пароля эта CLI пока не предоставляет.
   `setup_local.py` предназначен для локального режима и не используется в production.

```bash
# One-time restore into a NEW EMPTY volume. Do not run against a working site.
docker compose --env-file .env.production -f compose.production.yaml build
docker compose --env-file .env.production -f compose.production.yaml create migrate
# bundle/data contains local.db, media/ and sports-sync/; copy contents, not its parent.
docker compose --env-file .env.production -f compose.production.yaml cp ./bundle/data/. migrate:/app/data/
docker compose --env-file .env.production -f compose.production.yaml run --rm --no-deps --user root --cap-add CHOWN migrate chown -R app:app /app/data
docker compose --env-file .env.production -f compose.production.yaml -f compose.https.yaml up -d --build
```

При пустом volume миграции создадут пустую БД, а не перенесут содержимое локального
сайта. Проверяйте матчи, составы, таблицы и фото после восстановления. Команда
`docker compose down -v` удаляет постоянные данные — для обычного обновления она не нужна.
При обновлении исходников повторно используйте тот же Compose project и volume.
Перед обновлением сохраните резервную копию.

Команды `cp` и `chown` выше выполняются один раз при восстановлении в пустой volume.
Их повторение поверх действующего сайта перезапишет данные. Для повторного восстановления
остановите API и все записи, создайте независимую резервную копию и проверяйте восстановление
в отдельном новом volume. `compose.https.yaml` ограничивает тело запроса 9 МБ; существующий
лимит загрузки приложения — 8 МБ. Caddy в этой конфигурации не добавляет внешний limiter
входа: перед публичным запуском настройте его в edge proxy/WAF. В самом приложении уже
действует ограничение попыток входа; для SQLite используется один API-процесс.

## Фронт и авторизация

В GitHub Pages задайте repository variable `VITE_API_BASE_URL=https://api.club.example`.
Это публичный адрес сервера; ключи FIBA и пароли в переменные `VITE_*` не помещают.
Полная инструкция Pages находится в репозитории фронтенда.

Предпочтительная схема для админки: `https://club.example` (GitHub Pages с custom
domain) + `https://api.club.example`. Браузер считает их одним site; используйте
`APP_COOKIE_SAMESITE=lax`, Secure cookie и точный CORS origin.

`https://account.github.io` и `https://api.provider.example` считаются разными sites.
Для такой схемы предусмотрен `APP_COOKIE_SAMESITE=none` (только вместе с Secure/HTTPS),
но браузер всё равно может блокировать сторонние cookie. Публичные страницы смогут
получать данные; вход и редактирование требуют отдельной проверки в целевых браузерах.
Для надёжной админки используйте общий домен или публикацию админки с тем же origin,
что и API. Одного изменения CORS для этого недостаточно.

## Проверка перед переключением

Проверьте HTTPS; список матчей и таблицу 2026/27; статистику обоих составов;
фотографии истории и капитанов; вход и выход администратора; загрузку фотографии;
сохранение правки после перезапуска; статусы АСБ раз в час и FIBA раз в сутки;
восстановление из резервной копии на отдельном тестовом томе.
После переключения убедитесь, что локальный и облачный сборщики не работают
с разными независимыми базами, ожидая общей истории изменений.
